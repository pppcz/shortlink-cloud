# 面试讲述指南 · shortlink-cloud

> 这份文档的作用：把代码里的设计决策翻译成**面试时能讲出来的话**。
>
> 使用方式：面试前过一遍「一分钟版本」，被追问时翻到对应决策点看「怎么答」。
> 每个决策都标了**代码位置**，被要求"指给我看"时能立刻打开。

---

## 一、一分钟版本（自我介绍里怎么提这个项目）

> 我做了一个高并发短链平台，技术栈是 Spring Boot 3 + MySQL 8 + Redis 7 + RabbitMQ。
> 功能上就是短链生成、跳转、访问统计、限流和管理后台，但**重点不在功能，在于把
> "读多写少"场景的几个典型问题落地解决了一遍**：
> 缓存穿透用布隆过滤器加空值标记、缓存雪崩用 TTL 抖动、发号用 Redis INCR 加数据库
> 唯一索引兜底、统计用 MQ 异步削峰并保证不丢数。
>
> 印象最深的是两个坑：一个是短链如果用 301 会被浏览器永久缓存导致统计失真，
> 必须用 302 加 `no-store`；另一个是**布隆过滤器重启后必须预热**，
> 不然内存位图一丢，所有存量短链都会被判定为"不存在"，直接全站 404。

这个开场的好处：**两个坑都是"踩过才知道"的细节**，天然引导面试官往深里问。

## 二、按决策点展开（被追问时用）

### 决策 1：跳转为什么用 302 而不是 301

**代码位置**：`controller/RedirectController.java`

**怎么答**：

> 301 是永久重定向，浏览器会把它缓存下来，用户第二次点同一个短链**根本不会请求到我的服务**。
> 对一个靠统计卖点的短链平台来说，这等于统计数据直接失真。
> 所以用 302 临时重定向，并且显式加上 `Cache-Control: no-store` 和 `Pragma: no-cache`，
> 确保每次访问都真实回源。

**如果面试官问"那性能不就差了"**：

> 确实牺牲了浏览器缓存带来的收益，但短链跳转的成本主要在服务端缓存命中，
> 我的 Redis 缓存命中后整个过程不碰数据库，实测瓶颈不在这一层。
> 这是**统计准确性 vs 带宽成本**的取舍，我选了前者，因为短链平台的核心价值就是数据。

---

### 决策 2：缓存穿透的三层防御

**代码位置**：`service/impl/ShortLinkServiceImpl#resolve`、`ShortLinkCacheManagerImpl`

**怎么答**：

> 跳转链路我做了三道闸，顺序是有讲究的：
>
> 1. **布隆过滤器**：判定"一定不存在"就直接 404。这一步不碰 Redis 的数据面，
>    恶意扫描随机短码时能挡住绝大多数请求。
> 2. **Redis 缓存**：命中就直接跳转。这里还有一个**空值标记**——
>    如果数据库查不到，我会往 Redis 写一个空值，TTL 只有 60 秒。
>    这样同一个不存在的短码被反复请求时，第二次就不会再打数据库。
> 3. **回源数据库**：只有前两关都没命中才查库，查到后回写缓存。
>
> **为什么空值 TTL 只有 60 秒**：短链可能是刚被创建的，如果空值缓存太久，
> 新短链会被自己的空值标记挡住。60 秒是个折中。

**如果面试官问"布隆过滤器误判怎么办"**：

> 布隆过滤器只会假阳性（说不存在的一定不存在，说存在的不一定存在），
> 所以误判的后果是"多查一次缓存和数据库"，不会漏掉真实数据——这个方向是安全的。
> 我配的误判率是 0.001。

---

### 决策 3（重点）：布隆过滤器重启后必须预热

**代码位置**：`config/BloomFilterWarmUpRunner.java`、`ShortLinkCacheManagerImpl#warmUpBloomFilter`

**这是最能体现"踩过坑"的一点，建议主动讲**：

> 布隆过滤器有个特性：**只能加不能删，而且位图在内存里**。
> 进程重启后位图就没了，如果直接上线，**数据库里所有存量短链都会被判定为"一定不存在"，
> 全站 404**。
>
> 所以我在 `ApplicationReadyEvent` 里做了一次预热：把数据库里所有短码重新灌进布隆过滤器。
>
> **为什么放在 `ApplicationReadyEvent` 而不是 `@PostConstruct`**：
> `@PostConstruct` 执行时数据源和 Flyway 迁移可能还没就绪，读库会失败。
> `ApplicationReadyEvent` 才是"应用真正可以服务了"的时点。
>
> **而且预热失败不能阻止启动**：我 catch 了异常。因为预热失败只会退化成
> "所有请求都回源数据库"，功能仍可用，只是失去防穿透保护——
> 这比服务起不来要好。

**如果面试官问"那多实例部署呢"**：

> Redisson 的布隆过滤器位图是存在 Redis 里的，多个实例共享同一份，
> 所以只有第一个实例需要真正预热，后面的实例检查到 `isExists()` 会跳过。
> 这也顺便让预热是幂等的。

### 决策 4：缓存雪崩与 TTL 抖动

**代码位置**：`ShortLinkCacheManagerImpl#ttlFor` / `#jitter`

**怎么答**：

> 两个处理：
>
> 1. **TTL 加 ±20% 随机抖动**。如果一批 key 同时写入、TTL 都是 1 小时，
>    那 1 小时后它们会同时失效，所有请求瞬间压到数据库上——这就是雪崩。
>    抖动把失效时刻打散。
> 2. **TTL 取 `min(配置 TTL, 距短链过期秒数)`**。这个容易被忽略：
>    如果一条短链 3 分钟后过期，而缓存 TTL 是 1 小时，
>    那么短链过期后缓存里还是旧数据，**过期了还能跳转**。
>    取 min 之后缓存最多活到短链过期那一刻。

### 决策 5（重点）：MQ 异步统计，刷盘成功才 ack

**代码位置**：`mq/LinkAccessConsumer.java`、`service/impl/StatsServiceImpl.java`

**怎么答**：

> 跳转是读操作、统计是写操作，两者性能量级差很多。
> 所以跳转接口**只投递一条 MQ 消息，完全不写数据库**，PV/UV 由消费者异步累加。
>
> 消费者的设计是**内存攒批 + 定时刷盘**：攒到 500 条或者每 2 秒刷一次。
> 目的是把写放大降下来，避免高峰期逐条 INSERT 把数据库打满。
>
> **最关键的一点是 ack 时机**：我是**刷盘成功之后才 ack**。
>
> 如果反过来先 ack 再写库，一旦写库失败消息就永久丢了，统计静默少数据，
> 而且这种错误很难被发现。现在的做法最坏情况是"重复消费"，
> 而重复消费的代价是可控的——UV 靠数据库唯一键天然去重，
> PV 是按 `(短码, 日期)` 聚合后一次性累加的，重复投递不会重复计数。
>
> **这是一个明确的取舍：我选"最多重复消费"，而不是"可能丢数据"。**

**如果面试官问"那 MQ 挂了跳转会不会失败"**：

> 不会。生产者在 `publish` 里 catch 了所有异常，只打告警日志。
> 统计是旁路能力，MQ 抖动不该让用户跳转失败。
> 代价是这段时间的统计数据会丢，但跳转可用性优先。

### 决策 6：UV 去重为什么要单独开一张表

**代码位置**：`t_link_uv_log` 建表语句、`StatsServiceImpl#aggregate`、`LinkUvLogMapper#tryInsertUv`

**这个点很能体现思考深度，建议讲**：

> 统计表里只有一个"当天 UV 数字"。问题是：**当一条访问消息进来时，
> 我怎么知道这个 IP 今天是不是已经来过了？** 光看聚合表回答不了这个问题。
>
> 我的做法是单独建一张 `t_link_uv_log`，唯一键是 `(short_code, stat_date, ip_hash)`，
> 插入用 `INSERT IGNORE`，**只有返回 1（真的插进去了）才给 UV 加一**。
>
> **为什么用 INSERT IGNORE 而不是"先查后插"**：并发下"查不到就插入"会有竞态，
> 两个线程同时查到不存在、然后都插入，UV 就多算了。
> 把去重交给数据库唯一键才能保证原子性。

**如果面试官问"这张表不会无限大吗"**：

> 会，这正是它的风险点。所以我加了定时清理任务
> （`DataRetentionServiceImpl`），按天分批删除超过保留期的记录。
> 分批是为了避免长事务阻塞主从复制。

### 决策 7：Lua 限流与 fail-open

**代码位置**：`resources/lua/rate_limit.lua`、`service/impl/RedisRateLimitService.java`

**怎么答**：

> 限流是典型的"读-判断-写"复合操作，如果在应用侧分两步做，
> 高并发下会出现"检查通过后并发写"导致超发。所以用 Lua 脚本放在 Redis 里原子执行。
>
> 脚本里两个细节：
> 1. `INCR` 和 `EXPIRE` 必须在同一段 Lua 里。如果分开执行，
>    可能出现"INCR 成功但 EXPIRE 没执行"，这个 key 就永不过期，那个 IP 会被永久限流。
> 2. **只在计数为 1 时设置过期**。如果每次请求都 `EXPIRE`，TTL 会被不断刷新，
>    窗口就永远不会结束。

**如果面试官问"Redis 挂了怎么办"**：

> 我做的是 **fail-open**，也就是放行。
>
> 理由：限流是为了保护系统，不是业务正确性的一部分。
> 如果因为限流组件自己故障就拒绝全部正常流量，损失远大于短暂放行。
> 这个取舍写在 `RateLimitResult.failOpen()` 的注释里。

**如果面试官问"固定窗口有什么问题"**：

> 固定窗口在边界处理论上允许 2 倍瞬时流量穿过。
> 我选它是因为一次 `INCR` 就能判定，比滑动窗口省一次 ZSET 写入，热路径开销更低。
> 对这个场景（每 IP 每秒几十次）够用了。如果要求严格，
> 应该改用滑动窗口或者令牌桶。

### 决策 8：发号器与唯一性保证

**代码位置**：`service/RedisSeqShortCodeGenerator.java`、`ShortLinkServiceImpl#persist`

**怎么答**：

> 用 Redis 的 `INCR` 发号，按天分 key，值再转 Base62 变成短码。
> `INCR` 是原子的，多实例部署也不会重复。
>
> **但我没有只依赖 Redis**：
> 1. 数据库上 `short_code` 有唯一索引，这是最后一道防线。
> 2. 插入时捕获 `DuplicateKeyException` 重试，最多 5 次。
> 3. 如果 Redis 整个不可用，降级到本地时间戳+自增序列的发号器，
>    靠上面两条兜住。
>
> **唯一索引刻意不含 `deleted` 字段**：短码一经分配就永久占用。
> 否则短链被逻辑删除后，短码会被重新分配出去，
> 老的短链（比如已经印在二维码上的）就会跳到别人的链接上——这是串链事故。

### 决策 9：测试策略（单元 vs 集成）

**代码位置**：`src/test/java/.../integration/`、`pom.xml` 的 `integration` profile

**怎么答**：

> 我分成两层：
>
> - **10 个单元测试类**，全部 mock 掉 Mapper、Redis、MQ。
>   跑得快，适合每次提交都跑。覆盖的是业务编排逻辑——
>   比如"自动发号冲突时重试""UV 只统计首次访问""限流阈值边界"。
> - **2 个集成测试类**，用 Testcontainers 启动真实 MySQL 8 + Redis 7 + RabbitMQ。
>   默认不跑（需要 Docker），加 `-Pintegration` 才执行。
>
> **集成测试存在的理由很具体**：单元测试全是 mock，
> 它验证不了"SQL 语法对不对""Flyway 迁移能不能在真实 MySQL 上跑通"
> "JSON 消息能不能被反序列化"。
> 比如清理任务的 `DELETE ... LIMIT` 是 MySQL 方言，
> H2 根本不支持，只能靠真实 MySQL 验证。

**如果面试官问"这些测试都跑过吗"**：如实说：

> 集成测试和单元测试的**代码**都写了，但我开发环境的沙箱没有 Docker 也连不上外网，
> 所以我在项目里配了 GitHub Actions，推送后会自动跑完编译、单元测试、
> 集成测试和前端类型检查。**结论以 CI 的实际结果为准，我不想凭猜测说"测试通过"。**

> ⚠️ **这一点必须诚实**。面试官如果追问"测试跑了吗"，说"跑了"然后被要求
> 现场演示会很难看。承认环境限制反而显得靠谱，而且你确实配了 CI 来兜底。

## 三、被问"这个项目有什么不足"时怎么答

**别硬撑，主动说出问题会加分**。可以这样讲：

> 有几个我知道但没做的：
>
> 1. **`t_link_access_log` 没有分区**。我考虑过按 `access_date` 做 RANGE 分区，
>    但分区要求把分区列纳入主键，而且新增分区要提前建，用硬编码日期会过期。
>    对一个每天跑一次清理的中等规模系统，分区带来的复杂度大于收益，
>    所以我先用索引 + 分批 DELETE。真到单表过亿、需要秒级 DROP 历史时再上分区。
> 2. **限流是单机视角的**。Sentinel 的规则是本地内存规则，多实例下每个实例各自计数。
>    如果要精确的集群全局限流，得换成 Redis 集中计数——但那会增加一次 Redis 往返。
> 3. **没有做访问日志的异步压缩或归档**，直接删除。如果要保留历史明细做审计，
>    应该先转存到对象存储。
> 4. **前端没有自动化测试**，只有 TypeScript 类型检查作为门禁。

**为什么这样答有效**：每一条都是"我知道正确做法是什么，但因为某原因选了当前方案"，
而不是"我没想到"。前者体现判断力，后者只是遗漏。

## 四、可能被问到的技术细节（速查）

| 问题 | 答案要点 |
|---|---|
| 为什么用 Redisson 不用 StringRedisTemplate | 需要布隆过滤器和分布式锁，Redisson 直接提供且位图持久化 |
| 为什么缓存值用 JSON 不用 JDK 序列化 | 可读可调试、跨语言、避免反序列化漏洞 |
| MyBatis-Plus 逻辑删除怎么配的 | `logic-delete-field: deleted`，查询自动加 `deleted = 0` |
| JWT 密钥长度要求 | HS256 要求 ≥ 32 字节，jjwt 会直接拒绝短密钥，我在启动时校验 |
| 为什么密码用 PBKDF2 不用 bcrypt | **如实说**：JDK 原生支持、零依赖，而且我能用等价 Python 实现交叉验证哈希；bcrypt 需要额外依赖，我在离线环境无法验证种子哈希正确性 |
| Sentinel 和 Redis 限流的分工 | Redis 按 IP 维度防刷（跨实例共享），Sentinel 做接口级总量兜底（本地快速失败） |
| 为什么时间列要冗余 `access_date` / `hour` | 避免对时间列做函数运算导致索引失效，报表按天查能走联合索引 |
| IP 为什么存 MD5 | UV 去重只需要"同一个 IP 得到同一个值"，存哈希减少敏感信息沉淀 |
| 乐观锁/悲观锁用了吗 | 没用。并发点靠 Redis 原子操作 + 数据库唯一索引解决，不需要应用层锁 |

## 五、现场演示建议（如果被要求跑起来）

**演示前一定先在本地跑一遍**，别现场第一次跑。

```bash
# 1. 起中间件
cp .env.example .env
docker compose up -d mysql redis rabbitmq

# 2. 起后端
cd backend && mvn spring-boot:run

# 3. 演示三条命令（README「冒烟测试」一节）
#    创建 → 跳转 → 统计
```

**演示顺序建议**（体现广度）：

1. Swagger 页面 `http://localhost:8080/swagger-ui.html` —— 展示接口设计
2. 创建短链 → `curl -I` 看 **302 和 no-store 响应头** —— 呼应决策 1
3. 管理后台 → 短链列表 → 点「统计」看 ECharts 图表 —— 展示前端
4. 打开 `docs/benchmark.md` —— **如果还没压测数据，主动说明并解释为什么不填假数据**

第 4 步如果处理得好是加分项：展示的是工程诚信，而不是"我数据很漂亮"。

## 六、这个项目最值得讲的三个点（如果时间有限）

1. **302 + no-store 的取舍** —— 说明你理解"统计准确性是这个产品的核心价值"
2. **布隆过滤器必须预热** —— 说明你踩过真实的坑，而不是照抄方案
3. **刷盘成功才 ack 的取舍** —— 说明你能在"丢数据"和"重复数据"之间做有意识的判断

这三点共同传达一个信息：**你不是在堆技术，而是在做取舍。**
这是面试官真正想看的。
